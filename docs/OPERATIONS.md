# Эксплуатация: как узнать, что всё сломалось, и что делать

Этот файл читают не когда всё хорошо, а когда сайт не открывается.
Поэтому здесь короткие команды и порядок действий, а не теория.

---

## 1. Жив ли сайт

```bash
curl -s https://knigomany.ru/healthz
```

| Ответ | Что значит | Что делать |
|---|---|---|
| `{"ok":true,...}` с 200 | сервер и база работают | ничего |
| `{"ok":false,...}` с 503 | сервер жив, **база не отвечает** | раздел 3 |
| ошибка соединения / таймаут | сервер не запущен или упал | логи хостинга, раздел 2 |
| 308 на другой адрес | открываешь не тот адрес | открой `PUBLIC_URL` из настроек |

`dbLatencyMs` в ответе — время запроса к базе. Больше 500 мс — база тормозит:
смотри план запросов и соединения, а не код.

## 2. Что произошло: логи

Логи структурированные, по одной JSON-строке на событие:

```json
{"time":"2026-11-17T09:00:00.000Z","level":"error","message":"request","meta":{"method":"GET","path":"/kniga","status":500,"requestId":"a1b2c3"}}
```

- `requestId` есть и в логах, и в заголовке ответа `X-Request-Id`. Человек
  называет его в письме — ты находишь ровно его запрос.
- Пароли и токены в логи не попадают: логгер их вырезает.
- Стек ошибки пишется только в лог и только вне продакшена — клиенту он
  не уходит никогда.

Полезные выборки (если логи в файле):

```bash
grep '"level":"error"' app.log | tail -50           # последние ошибки
grep '"status":500' app.log | tail -20              # пятисотки
grep 'a1b2c3' app.log                               # всё по одному запросу
```

## 3. База не отвечает

1. Проверь, что база запущена (панель Neon/Railway).
2. Проверь строку подключения: `DATABASE_URL` не содержит лишних кавычек,
   `sslmode=require` на месте.
3. Проверь соединения: у бесплатных тарифов лимит, и приложение с пулом
   `max: 8` может его выбрать. Если так — уменьши пул в `src/config/database.js`.
4. Если база переехала (сменился хост) — обнови `DATABASE_URL` и перезапусти
   приложение: строка читается при старте.

Проверить снаружи, без приложения:

```bash
psql "$DATABASE_URL" -c 'select count(*) from users'
```

## 4. Сайт работает, но медленно

Сначала измерь, потом меняй код.

```bash
curl -s -o /dev/null -w '%{time_total}\n' https://knigomany.ru/knigi
```

- Медленные запросы (≥ 1 с) сами пишутся в лог как `медленный запрос`
  вместе с путём и длительностью.
- `/metriki` с токеном показывает `slowestMs`, распределение по статусам и память:

```bash
curl -s -H "Authorization: Bearer $METRICS_TOKEN" https://knigomany.ru/metriki
```

- В тестах есть бюджет запросов: карточка книги делает ≤ 40 SQL-запросов на
  20 рецензий (факт — 21). Если станет больше, тест упадёт раньше, чем люди
  заметят.

## 5. Бэкапы

```bash
DATABASE_URL='postgres://...' npm run backup
```

Скрипт делает дамп, проверяет, что архив целый и в нём есть наши таблицы,
и удаляет файлы старше 14 дней. Бэкап без проверки восстановления — самообман,
поэтому рядом есть второй скрипт:

```bash
TARGET_URL='postgres://.../knigomany_restore' npm run restore:check backups/knigomany-2026-11-17.sql.gz
```

Он разворачивает дамп в **отдельную** базу и проверяет, что пользователи,
книги и таблица миграций на месте.

Расписание (cron на любой машине, где есть `pg_dump`):

```cron
# бэкап каждый день в 3:40
40 3 * * * cd /srv/knigomany && DATABASE_URL='...' ./scripts/backup.sh >> /var/log/knigomany-backup.log 2>&1
# проверка восстановления раз в неделю
30 4 * * 1 cd /srv/knigomany && TARGET_URL='...' ./scripts/restore-check.sh backups/$(ls -t backups | head -1) >> /var/log/knigomany-restore.log 2>&1
```

## 6. Мониторинг доступности

```cron
* * * * * cd /srv/knigomany && SITE=https://knigomany.ru ./scripts/monitor.sh
```

Скрипт дёргает `/healthz` и главную, проверяет код ответа и время, а при
проблеме возвращает код 1 и (если заданы `TELEGRAM_BOT_TOKEN` и
`TELEGRAM_CHAT_ID`) пишет в Telegram.

Проверить, что уведомление действительно приходит — обязательно: останови
приложение на минуту и посмотри, пришло ли сообщение.

## 7. Что делать, если сломали данные

1. Останови приложение: пока оно пишет, восстановление бессмысленно.
2. Разверни последний бэкап в отдельную базу, проверь `restore-check`.
3. Сравни: сколько записей потеряется. Если потеря большая — сначала выгрузи
   текущее состояние (`pg_dump`), чтобы не потерять его окончательно.
4. Переключи `DATABASE_URL` на восстановленную базу, запусти приложение.
5. Восстанови то, что появилось после бэкапа, руками — по логам и уведомлениям.

## 8. Аналитика для владельца

`/admin/svodka` — цифры, которые нельзя накрутить:

- **читателей всего** — реальные аккаунты без удалённых;
- **были за неделю** — у кого `lastActiveAt` за 7 дней;
- **вернулись** — зарегистрировались раньше недели и были на этой неделе;
- **топ книг** — по числу полок и дочитываний;
- **чек-лист** — что поправить (нет почты, нет описаний, один админ).

Возврат — главная цифра. Рост регистраций без возврата означает, что люди
заходят и не находят причины остаться.

### Воронка и «где уходят»

На той же странице две таблицы, которые отвечают на вопрос «что чинить»:

- **воронка за 30 дней** — регистрация → добавил книгу → дочитал → написал
  рецензию. Считается по когорте новых, а не по всей истории. Смотри не на
  абсолютные числа, а на долю от предыдущего шага: если между «добавил
  книгу» и «дочитал» теряется 70 %, проблема не в привлечении;
- **где уходят** — последний шаг тех, кто молчит дольше недели. Под каждой
  строкой написано, что обычно означает этот провал: «первый экран не
  убеждает», «полка есть, но до чтения не дошло», «нет повода написать
  рецензию», «сделал всё и не вернулся».

Как читать: правку делают по одной цифре за раз. Если провал на первом
шаге — правим главную и регистрацию; если на втором — подсказки на полке;
если на четвёртом — повод возвращаться (дайджест, клубы, «Книжный год»).

## 8.1. Рассылка писем

Дайджест запускается не таймером внутри приложения, а командой или cron —
иначе при двух инстансах письма уйдут дважды.

```bash
npm run digest:dry     # пробный прогон: собрать письма, ничего не отправляя
npm run digest         # отправить
npm run digest:stats   # что ушло и что сломалось за 30 дней
```

В админке: `/admin/rassylka` — счётчики, журнал и запуск с галочкой
«пробный прогон». Полные правила и инструкция для cron — `docs/DIGEST.md`.

Что проверить, если письма не уходят:

| Симптом | Причина | Что делать |
|---|---|---|
| в логе `[mail:dev]` | не задан `RESEND_API_KEY` и `SMTP_HOST` | настроить транспорт, раздел про переменные |
| `failed` у всех адресов | домен не верифицирован или неверный `MAIL_FROM` | проверить домен в Resend |
| `failed` у одного-двух | ящик не существует или переполнен | это нормально, письмо не повторяем |
| писем нет, ошибок нет | у людей выключена галочка | цифра «можно написать сейчас» в админке |

## 9. Кто что может

| Роль | Может |
|---|---|
| гость | каталог, книги, профили, клубы |
| читатель | своё: полка, рецензии, сообщения, клубы |
| модератор | жалобы, скрытие, блокировки, сводка |
| админ | всё выше + роли |

Скрытие рецензии и блокировка пишутся в журнал, который не удаляется вместе
с аккаунтом автора: история модерации должна переживать удаление.

## 10. Чек-лист после любого деплоя

- [ ] `/healthz` → 200
- [ ] главная, каталог, карточка книги открываются
- [ ] вход демо-пользователем работает
- [ ] регистрация нового аккаунта → письмо пришло
- [ ] `/sitemap.xml` и `/robots.txt` отдают адреса на своём домене
- [ ] `/admin/svodka` открывается у админа и закрыта для читателя
- [ ] `npm run digest:dry` собирает письма (ничего не отправляя)
- [ ] `/otpiska` открывается без входа
- [ ] в логах нет `error` за первые 10 минут
